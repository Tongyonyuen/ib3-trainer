## 一、结论速查

| 问题 | 答案 |
|---|---|
| 暗火数值上限 | **理论上无上限**：`1000 + GemTier×500`，GemTier 是 Byte(0~255) → 最高 **128500** |
| 光谱数值上限 | `1000 + GemTier×250`（**2026-10-08 实测 Tier 255 → 64750**）。**升级路径原版未配置**，只能直接改 Tier |

| 官方模板有几档 | 只有 **+500**（`UberElementalAttackGem`）和 **+1000**（`_100`）；`_200` 是本仓库自定义 |
| 不改 ini 能拿到多高 | 无上限（靠反复融合），但**每融一次要 2 颗 400 元素宝石** |
| 跨端（手机）能用吗 | **能**——融合产物名字是官方 `_100`，数值在实例字段里，手机端同公式自算 |
| 什么不能跨端 | 走自定义 `_200` 模板直购的那类（值全靠查 ini 表） |

## 二、数值公式（三样本实测）

同一存档内三颗同名宝石 `UberElementalAttackGem_100`：

| 宝石 | GemTier | CookedGemVar | 游戏内显示 |
|---|---|---|---|
| 直购 | 0 | 0 | 1000 |
| 融合 1 次 | **1** | 50 | **1500** |
| 融合 2 次 | **2** | 50 | **2000** |

```
显示值 = 模板基础值 + GemTier × RecipeBoostAmount
       = 1000 + GemTier × 500          （暗火；_100 模板的 RecipeBoostAmount=500）
```

**是加法，每次融合 +500。**

> **乘法假设的反证**：若为 `基础值×(1+cook/100)`，则 1000 → 1500 → **2250**，但实测第三颗是 **2000** → 乘法排除。

**光谱（Rainbow）——数值公式已实证；升级路径原版未配置**（2026-10-08 用户实测）

这两件事必须分开说，否则容易记混：

| | 结论 |
|---|---|
| **升级路径** | **原版 ini 里就没配置**。`RainbowElementalAttackGem_100` 没有可用的 `RecipeMatch` / `MPParent` 链 ⇒ **熔炉无法升级光谱**。这不是缺陷，是原版本来就没这条配方（印证 README 的「实测无法融合」） |
| **数值公式** | **`显示值 = 1000 + GemTier × 250`** —— 与暗火同族、**基数同为 1000** |
| **怎么验的** | 光谱实例**自带 `GemTier` 字段**，所以可以**直接改 Tier**（训练器「宝石·背包」页的 Tier 输入框）。改成 **Tier 255 → 游戏内显示 64750** |

反推校验：`64750 = 1000 + 255 × 250` —— 与 `_100` 模板的 `RecipeBoostAmount=250` **精确吻合**。
也就是说原先"光谱每次 +250（未实测）"的**预期是对的**，只不过到达高 Tier 的途径不是融合，而是直接改字段。

⚠ 两条边界：

- **这不改变「光谱 1000 是正常玩法终点」**：正常游戏里没有任何提升光谱 Tier 的途径，只有改内存/存档才行。
- 改 Tier 仍需 `CookedGemVar=50`（"已融合"标记）游戏才会承认 —— 训练器改 Tier 时会**自动补**这个标记。
  若手动改存档，记得同时把该字段设为 50，否则切场景重建背包时 Tier 会被归零。
  （`RainbowElementalAttackGem_100` 就在受影响的 15 个加法型模板之列。）

**`CookedGemVar` 不是数值驱动**：融合过恒为 50、未融合为 0；两颗同为 50 却分别显示 1500 / 2000，直接证伪。

`GemTier` 对**元素宝石**另有含义（= `UpgradeTier` 下标，1 基）：
`FireGem`/`IceGem` 等 = `UpgradeTier[GemTier-1] × (1 + RandomAddPct)`，
`UpgradeTier=[5,25,50,100,200]`、`MaxRandomAddPct=1.0` → 满 roll = 200×2 = **400**。

## 三、两条刷店命令（行为不同，勿混）

| 命令 | 产出去向 | pct 掷法 | 能否出 400 |
|---|---|---|---|
| `setplayercreatenewlistofstoregems 1 <模板名> 0 <数量> 1` | 随身商店 `CurrentStoreGems` | **随机**（0.02~0.8） | ✗ |
| `setplayergems 0` | 随身商店 `CurrentStoreGems` | **元素族拉满 1.0** | ✓ |

`setplayergems 0` 产出 **154 颗**，结构大致是「每个模板 × 常规/In/Out/Uber 四种」：

```
FireGem      tier=5  pct=1.0  → 400   ← 融合素材就用这个
FireGemIn    tier=1  pct=0.5  → 750   （Restrict=1/2，不可装备）
FireGemOut   tier=1  pct=0.5  → 750
UberFireGem  tier=0  pct=0.0  → 500
```

八个元素族（Fire/Ice/Elec/Poison/Light/Dark/Water/Wind）全部如此。
另**直售**暗火三档：`UberElementalAttackGem`(500) / `_100`(1000) / `_200`(2000，需自定义 ini)。

## 五、跨端判定

存档里每颗宝石记录只有 6 个字段：

```
{ GemName, GemTier, CookedGemVar, RandomAddPct, bShowBadge, Boost }
```

融合产物的数值完全由 `GemName`（官方 `_100`）+ `GemTier`（实例）决定 → **手机端只要跑同一套代码就能还原同样数值，不需要任何 ini 改动**。

**对照**：`_200` 模板直购的那类，`GemTier=0`、值 2000 全靠查 ini 表 → 手机端没有 `_200` 表项 → 不跨端。

> ⚠️ 手机端行为未实测，属推断。验证方法：把存档（`_SwordSaveX_0-0.bin`）替换到手机端存档位置，看融合产物显示值是否为 1000+N×500。

## 八、存档直改路线：哈希层已破译，但仍被挡住（2026-10-07 实测）

**动机**：不改 ini、不进熔炉，直接给任意数值（如 3000）。

**探明的机制** —— `LocalFileHeaderCache`（1284 字节，同样是 `"yeK "`+AES-256-ECB）：

```
缓存条目 = [SHA1 十六进制(40 字符) + NUL][路径长度 i32][相对路径][文件名长度 i32][文件名][...]
校验值   = SHA1( 解密明文 截断到 (最后一个 "None\0" 的位置 + 5) )
```

- 验证 A：`_CTN`（内容 `2026.10.07-11.17.17`，真实长度 24）→ `sha1(plain[:24])` **命中**缓存值 ✓
- 验证 B：存档 → `sha1(plain[:308152])` **命中** ✓（308152 = 最后一个 `None\0` @308147 + 5）
- `_SwordSaveX_0-0.bin` 与 `_BackupX_0-0.bin` 在缓存里共用同一个哈希（两者内容原本相同）

**做过什么**：改存档 1~2 字节 → 按上述规则重算 SHA1 → 同步改写缓存两条记录（长度不变）→ 回读校验全部 OK。

**结果：游戏重启后仍显示原值**（两次验证）。→ 哈希层**不是**唯一关卡；或游戏根本不从 `Cloud\` 目录读这个档（另有来源）。

**⚠️ 已完整回滚**（主档 / 备份档 / 缓存全部还原且哈希自洽）。
原档备份：`_tmp/BEFORE_3000_112003.bin`、`_tmp/BEFORE_CACHE_112256.bin`。

**未探明的怀疑点**（留给后续）：`_CTN`（时间戳）、`_CTRB`、`_CurrentSlot`、`CloudStorage.ini` —— 疑似"本地 vs 云端"的时间戳仲裁：本地档被外部改动后时间戳对不上 → 游戏改用云端/内存副本。

**结论**：现阶段"直接改存档发宝石"**不可行**，绕开熔炉的捷径不成立；请走第四节融合路线。

## 七、存档字段速查（解密后）

字段值位于 `'None'` 字符串**之后**那一个字节（ByteProperty 在此移植版序列化为 `'None'+数字`）——
**不要**把 `'None'` 的长度前缀 `05` 误读成字段值（本次曾因此误判）。

```
GemName       NameProperty    名字（决定模板基础值）
GemTier       Byte            融合次数（暗火）/ UpgradeTier 下标（元素宝石，1 基）
CookedGemVar  Byte            烹饪标记：融合过=50，未融合=0（不参与数值）
RandomAddPct  Float           随机加成（元素宝石用；暗火固定 0.0）
bShowBadge    Bool            是否显示角标
Boost         Byte            未观测到变化
```
