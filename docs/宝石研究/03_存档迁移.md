## 二、`LocalFileHeaderCache` 完整破译（100% 结构确定）

解密后**体长 1280 字节**（磁盘 1284 = 4 字节 `"yeK "` 魔数 + 1280，无额外填充）。

### 2.1 布局

```
[0]  i32  ver      = 2
[4]  i32  f1       = 0        （疑似"远程列表"计数，本机恒 0）
[8]  i32  f2       = 0
[12] i32  count    = 11
[16] 条目 × count  （紧邻，无分隔）
尾部 2 字节 0x0000
```

**每条目**（顺序即文档下标，0 基）：

```
i32   hashStrLen      = 41            // 40 个十六进制字符 + NUL
char  sha1hex[40]     + NUL
i32   pathLen                         // 相对路径长度（含 NUL）
char  relPath[...]    + NUL           // 形如 ..\..\SwordGame\Cloud\_CTN
i32   nameLen                         // 文档名长度（含 NUL）
char  docName[...]    + NUL           // 云文档名，如 CTN / SwordSaveX_0-0.bin
i32   contentLen                      // ★ 权威明文长度（参与哈希的字节数）
i32   0                               // 未见非 0
```

> ⚠️ **本仓库此前记的"哈希 = SHA1(明文截断到最后一个 `None\0` + 5)"只是巧合**。
> 真正规则是 **`sha1 = SHA1(解密明文的前 contentLen 字节)`**，
> `contentLen` 就明明白白写在缓存条目里（第 7 个字段）。存档的 `contentLen` 恰好等于"最后一个 `None\0`+5"。
> 对 `_CTN`（contentLen=24）、`_CTRB`/`_CurrentSlot`（contentLen=4）则完全不是那个规则。

|---:|---|---|---:|---|

## 三、文档列表 = 权威索引（内存实证）

在**运行中的进程**里搜 `..\..\SwordGame\Cloud\`（hex `2e2e5c2e2e5c...`），
命中 6 处、聚集在 `0x7FF4F733CD41`–`0x7FF4F733CF55`；把该区块 dump 出来，
**就是上面 11 条列表的逐字节副本**（`0B 00 00 00` 计数、`29 00 00 00` 哈希长、40 位哈希、路径、文档名、contentLen 全部对得上）。

⇒ **游戏启动时会读取 `LocalFileHeaderCache`，并在内存里持有这份列表。**

**`SwordSaveX_2-0.bin` 在整个进程内存里 0 命中** ⇒ 2 号槽不是"没读到"，而是**列表里压根没有它**。

### 3.1 `CloudDocIndex` 就是"自己在列表里的下标"

`_SwordSaveSlotX_N.bin` 解密后是 UE3 tagged property：

```
CharacterName   StrProperty   '赛瑞斯'
CloudDocIndex   IntProperty   ← 关键
SaveFiles       StructProperty (含 SaveFileMetaData / CurrentMap / 等级 / 时长 等)
```

| 文件 | CloudDocIndex | 列表里同下标是什么 | 结论 |
|---|---:|---|---|
| `_SwordSaveSlotX_0.bin` | **5** | `SwordSaveSlotX_0.bin` | ✅ 命中自己 |
| `_SwordSaveSlotX_1.bin` | **7** | `SwordSaveSlotX_1.bin` | ✅ 命中自己 |
| `_SwordSaveSlotX_2.bin` | **11** | —（列表只到 10） | ❌ **越界** |

⇒ `CloudDocIndex` 是**绝对下标**，一旦列表顺序/长度变了就错位。10 月 6 日、10 月 7 日两次快照里
5/7/11 完全一致 ⇒ 这个下标是**写死在槽文件里**的，不随会话变化。

> **由此可解释 2 号槽为什么永不出现**：它的槽元数据指向下标 11，而列表只有 11 条（0~10）。
> 这看起来就是**一次失败的导入留下的残骸**（4 个文件被塞进目录，但从没走完登记流程）。

## 七、那"换整个 Cloud\ 也没用"是为什么（推断 + 待验证）

> 本节为**推断**，第六节只证明了"控制良好的改档能生效"；整目录替换的负面对照本轮**未跑完**（时间窗用尽），
> 列为待验证。

按已证实的机制，整目录替换要成功，**换进去的那套必须自己内部自洽，并且与本机已有状态不冲突**。
最可能的失败原因，按可能性排序：

| # | 假设 | 为什么可能 | 怎么验 |
|---:|---|---|---|
| 1 | **换档时游戏还在运行** | 游戏每约 50 秒自动存档、切场景立即写盘；玩家复制完还没重启，运行中的实例已经把目录写回自己的状态 | 重启后立刻看 `_CTN` 是否被改成"现在" |
| 2 | **只换了主档，没换 `LocalFileHeaderCache`** | `contentLen` + SHA1 两侧对不上 → 该文档被视为"本地已改/待同步"，被跳过或回滚 | 已证：只改文件不改缓存必然不一致 |
| 3 | **换进去的一套与本机 `CloudDocIndex` 不匹配** | 若来源机的文档列表顺序/条数不同，`_SwordSaveSlotX_N.bin` 里的绝对下标会指错文档（2 号槽就是活标本） | 对比两侧 `CloudDocIndex` 与列表顺序 |
| 4 | 目标机器的 `_CurrentSlot` 指向一个来源机上不存在的槽 | 加载到空槽 → 看起来"没导入" | 把 `_CurrentSlot` 显式设成存在的槽号 |
| 5 | 玩家把文件夹放错了地方（放到 `E:\IB3\SwordGame\Cloud\`） | 游戏目录下**没有** `Cloud\`，容易误放 | 已证：真档只在"文档"那份 |

**已排除**：`PotentiallyManipulatedData`（见第八节）、`UnencryptedSave*.bin`、启动器、隐藏的第二份存储。

## 八、`PotentiallyManipulatedData` 追查（**不是**阻断层）

> 这条曾被怀疑是"一直没找到的未知校验层"。**证伪了。**

它是存档明文里的一条 **`IntProperty`**（4 字节），位于槽 0 主档偏移 `241657`、
槽 2 主档偏移 `46054`，值恒为 **1**。

**历史追踪**（多份快照对比）：

| 快照 | 时间 | 槽0 | 槽1 | 槽2 |
|---|---|---|---|---|
| `cloud_backup_20261005/` | 10-05 13:38 | **无该属性** | 无 | 无 |
| `cache_test/` | 10-05 14:12 | **无该属性** | 无 | 无 |
| `cloud_backup_20261006_boot/` | 10-06 00:21 | **1** | 无 | — |
| `_saves_backup_1049/` | 10-06 10:42 | **1** | 无 | — |
| `_tmp/BEFORE_3000_112003.bin`（改档实验前的锚点） | 10-07 | **1** | — | — |
| 当前 | 10-07 | **1** | 无 | **1** |

三条**独立**的反证：

1. **早于改档实验**：10-06 00:21 的快照里就已经 =1，而"直接改存档"实验是之后再做的。
2. **它与"能不能读"无关**：槽 0 长期带 `PotentiallyManipulatedData=1` 且正常游玩、正常存档、正常重启加载。
3. **它是"有则写、无则略"的条件属性**：槽 1 从头到尾**没有这个属性**（不是值 0，是整条不存在），
   而槽 1 一样能存档能加载——**说明它不是加载时的硬判定**。

**推断**：它是"这份数据在 PC/桌面路径上走过一遍（解密/重序列化）"的标记，属**上报/展示**性质，
同时参与 `CloudFilteringSaveLevel`（`SwordGame.ini` 里 =3）这类"哪些档值得往云上传"的过滤，**不影响本地读档**。

## 九、可用的迁移配方（在已证实机制上给出）

> ⚠️ 以下配方基于第六节已证实的机制；**其中第 2 步的"整目录"方式本轮未做正面对照**，
> 保守起见给了逐档迁移法。

### 9.1 逐档迁移法（推荐，机制已证实）

```
0) 关闭游戏（确认任务管理器里没有 IB3.exe）★ 这一步不能省
1) 备份接收方的整个 Cloud\ 目录
2) 记下来源方的槽号 N 与文档列表（用 mig_cache.py 枚举 LocalFileHeaderCache）
3) 把来源方的 4 个文件复制到接收方：
     _SwordSaveX_<N>-0.bin  _BackupX_<N>-0.bin
     _SwordSaveSlotX_<N>.bin _BackupSlotX_<N>.bin
4) 用 mig_verify.py 检查：
     接收方缓存里 <N> 那几条的 contentLen 必须与来源方一致；
     不一致就按 SHA1(明文[:contentLen]) 重算并原地改写 40 位哈希
5) 检查 _SwordSaveSlotX_<N>.bin 的 CloudDocIndex 是否等于它在接收方列表里的下标；
     不等就用（等长）字节替换改成正确下标
6) 把 _CurrentSlot 的 i32 值设成 N（4 字节内容，等长改写 + 同步缓存哈希）
7) 启动游戏
```

### 9.2 整目录替换法（保守版）

```
0) 关闭游戏
1) 备份接收方 Cloud\
2) 用来源方的 17 个文件整体覆盖（含 LocalFileHeaderCache）
3) 覆盖后用 mig_verify.py 确认 11 条全部 OK（应当全 OK，因为两侧一起换）
4) 用来源方的 _CurrentSlot 值核对槽号，必要时改成接收方想用的槽
5) 启动游戏
若第 3 步出现不一致 ⇒ 来源方那一套本身就不自洽，先修好它
```
