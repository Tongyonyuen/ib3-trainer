## 三、最可能的根因 + 修法（下一步照这个做）

**根因**：引擎认"真身"的路径只验 vtable 与金币，撞上玩家类的空壳实例就会认错。

```csharp
// EngineCall.cs
:328  static bool ValidAnchor(IntPtr h, long o)   // 只验：vtable ∈ KNOWN_VTABLES 且 +0x2070 金币 ∈ (0,1e15)
:407  static long PickExecutor(IntPtr h)          // 金币锚点优先，否则 OrderPlayerClass()[0]
:135  static bool LiveSane(IntPtr h)             // 也只验 vtable ⇒ ProbeRebind 认为"宿主还活着"就不重绑
```

实测本机进程里带玩家 vtable 的对象有 **8 个**：1 个真身（金币非 0 + 背包/商店装载）、
5 个金币与数组全 0 的影子、1 个金币非 0 但两数组都空、1 个是 vtable 假阳性。
旧锚点撞上被复用的堆对象时，**空壳照样通过 vtable+金币校验** ⇒ 绑到空壳 ⇒
金币/筹码/四维全在错的位置上读到平凡值（0 或 1），而且 `LiveSane` 一直 true ⇒ **从此不再重绑**，
这正是"打开就错、且一直错"的原因。

**同一类修法已有先例，直接搬**：`ib3trainer2\Tabs.Gems.cs` 的 `BodyScore`（约 `:457`）——
**背包装载 4 / 商店装载 4 / 金币 2 / 筹码 1，取最高分**，实测能稳定选中"装着数组的那个实例"。
把它搬到 `EngineCall.PickExecutor`，并让 `ValidAnchor`/`LiveSane` 用同一打分（≥4 才算"活着"），
再让 `ProbeRebind` 在"分数掉了"时也重绑。

⚠ `EngineCall` 是**注入层**，改它会波及所有命令注入 ⇒ **必须开着游戏实测**，别只看编译过。
改完至少验：金币/筹码/四维读数与游戏内一致；`fillsuperandmagicmeters`、`setplayergems 0` 仍能执行。

**本会话已加的闸（r12/r13，属"拒绝错绑"，不是根治）**：`Tabs.Growth.cs` 的 `AutoBindStats`
在"真身+固定偏移"读出的**四维全 0 或等级为 0** 时**放弃整组绑定**并写明日志（不动地址簿）；
`UpdateStatStatus` 不再把读数 0 报成"已定位"。
⚠ 作者明确纠正过：**四维全相同是合法加点**，已撤掉"全相同=绑错"的判据。

```

memtest.exe scanpat "E06BB64001000000" 40 40
# 逐个 dump 这几个字段，谁是真身一目了然：
#   +0x1FEC 背包 TArray{ptr,cnt,max}   +0x1FFC 商店 TArray
#   +0x2070 金币 i64                   +0x2094 筹码 i32
#   +0x1F10..+0x1F1C 四维 i32×4        +0x7B0 等级 / +0x1F3C 技能点
```

判据：真身 = 金币/筹码非 0 **且** 四维非平凡 **且** 至少一组数组装载；空壳 = 全 0 或全 1。
